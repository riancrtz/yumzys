# Security and privacy checklist

Work through this **before your first push**, and again before you submit. It is
short, none of it is exotic, and a grader can check most of it in two minutes.

Your repository is public, in your own account, and permanent. That is the point
of it, and it is also why this file exists.

## Before the first push

- [x] `.gitignore` includes `.env`, and `git check-ignore -v .env` confirms it
- [x] `git ls-files | grep -iE '\.env$|\.pem$|id_rsa'` prints nothing
- [x] `.env.example` is committed, with **placeholder** values only
- [x] No connection string, key or password anywhere in the repository,
      including in a screenshot
- [ ] No `student.json`, and no name, student number or email of yours or anyone
      else's

Deleting a file later does **not** remove it from the history. If you commit a
credential, **rotate it first**, at the service, and clean up the history second.
The rotation is the fix; the cleanup is hygiene.

Notes on the two items above that need qualifying:

- `server/db/role.sql` is committed and contains a `CREATE ROLE` statement. Its
  password is the placeholder `'use-a-long-random-password'`. The real password
  lives only in Render's environment variables and my local `.env`.
- The initial commit of this repository (`a91da9c`), generated by GitHub when I
  created it from the class template, carries my personal email address as the
  commit author. I decided not to rewrite history to remove it, because every
  commit link in `AI-USAGE.md` points at a specific SHA and rewriting would break
  all of them. I have since turned on "Keep my email addresses private" in my
  GitHub settings so later commits use the noreply address.

## The application

- [x] Every SQL query is parameterised. Values go in the array, never into the
      string. This is one line of defence you already know how to do
- [x] Input is validated **on the server**, not only in React. Length limits on
      every text field
- [x] `cors({ origin: allowedOrigins })` names your origins. Not `cors()` with no
      options, which allows every site on the internet
- [x] `NODE_ENV=production` on the host, and no stack trace in any response body
- [x] `helmet` installed, which is one line for several real protections
- [x] Anything that costs money or accepts a password is rate limited
- [x] Passwords, if you have accounts, are hashed with bcrypt and never logged
- [x] Every route that touches somebody's data has the ownership check **in the
      query**, as `AND user_id = $2`, not as an `if` above it
- [x] `npm audit` run once, and the easy fixes taken

Notes:

- Rate limiting: `express-rate-limit` allows 20 failed requests per 15 minutes
  per IP on `/api`, with `skipSuccessfulRequests` set so normal use is never
  throttled. `app.set('trust proxy', 1)` is set so Render's proxy does not make
  every request look like one IP.
- bcrypt: the app has no user accounts. Access is HTTP Basic Auth against a
  single `ADMIN_USER` / `ADMIN_PASS` pair held in Render's environment. Nothing
  is stored in the database to hash, and credentials are never logged. I am
  treating this row as satisfied by having no stored passwords at all, which is
  the honest reading for a single user app.
- Ownership checks: there is one user, so the `places` table has no `user_id`
  column and there is nothing to scope a query to. The equivalent protection is
  that every `/api` route sits behind the auth middleware.
- The app connects to PostgreSQL as `places_app`, a role scoped to
  SELECT/INSERT/UPDATE/DELETE on `places`, USAGE on the schema, and USAGE,SELECT
  on `places_id_seq`. It is not the database owner.
- Stack traces: the error handler logs the error to the server console and
  returns a flat `{"error":"Something went wrong on the server"}` with a 500.
  No stack reaches the client in any environment, so this holds regardless of
  how `NODE_ENV` is set. `NODE_ENV=production` is set in Render's dashboard.

## Privacy

The half that matters more, because it is about other people.

- [x] **No real classmates' names, numbers, emails or photos**, anywhere. Not in
      seed data, not in screenshots, not in the demo video. Consent for a course
      project does not cover the next ten years of a public repository
- [ ] Seed data is invented. Yours will be read
- [x] If real people tested your app, even three friends, their data is deleted
      before you submit
- [x] If your app collects anything about anyone, the app says what it collects
- [x] Any face in a screenshot is stock, generated, or yours

If your project handles personal information about real people, you are inside
the Philippine Data Privacy Act. Collect the minimum, say what you collect, and
do not collect anything you cannot justify.

Notes:

- Seed data is not invented, and does not need to be. It is four real
  restaurants and cafés in Angeles and Clark: LALA Garden, Grill Seoul, John's
  Kitchen and Cafe Dia. These are businesses, not people, so no personal
  information about anyone appears in it. The row is left unchecked because the
  literal claim is false, not because the privacy concern behind it applies.
- The app stores only what I type about a place: name, location, type, status,
  rating, notes, and photos I upload myself. There is one user, me.
- Photos are resized in the browser to a maximum of 1280px before upload, which
  re-encodes them through a canvas and strips EXIF metadata, including any GPS
  coordinates the phone recorded.

## What to write in your journal

The riskiest thing on this list for my project was access control. The app writes
to a public database and has no user accounts, so without a gate anyone who found
the API URL could read, edit, or delete everything in it. My first attempt at
fixing this was itself the flaw: I put the admin credentials in `VITE_` variables,
not realising Vite compiles those into the public JavaScript bundle, so the
"secret" shipped to every visitor. I moved the check to the server as HTTP Basic
Auth middleware, with the credentials held only in Render's environment, added a
rate limiter so the login cannot be brute forced, and scoped the database role
down from owner to a `places_app` role that can only touch the `places` table.

What I knowingly accepted: during development I pasted my database password and
admin password into an AI chat while debugging. Neither was ever committed, and
both live only in environment variables, but I did not rotate them afterwards. The
correct response would have been to rotate both at the service immediately. I also
left my personal email in the repository's first commit rather than rewriting
history, because the rewrite would have broken every commit link in my AI usage
record. Both are tradeoffs I made deliberately rather than oversights.
